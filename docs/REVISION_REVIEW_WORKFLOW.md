# Revision and delivery review (9.4.5 candidate)

Open a SurveySync project and choose **Revision & Delivery Review** from Home, QASync, or ReportSync. All records remain in that project's `Modules/QASync/ReviewWorkflow`; attachments are copied into `Attachments/ReviewWorkflow`, and review reports into `Reports`. Every action is recorded in the project audit chain. This workflow does not change canonical coordinates or source files.

**Compare revisions.** Upload a canonical point CSV with PointID, Northing and Easting, optionally Elevation and Description. Enter the exact CRS, horizontal units and vertical units used by the revised file; they must match nonempty project settings. The screen shows a project-coordinate movement overlay and a change table with ΔN, ΔE, ΔZ, distance, additions and removals. Where either side contains duplicate PointIDs, no automatic pairing occurs. Use explicit `{ "point_uuid": "old-record-uuid", "row": 2 }` matches; rows are CSV record ordinals including the header as 1. Unmatched duplicate records remain ambiguous and are never presented as additions or deletions. Comparison results retain the incoming file SHA-256 and project snapshot, not source bytes. Refresh and rerun after survey evidence changes.

**Field rechecks.** Select current QA findings, enter the crew and field instructions, then generate a crew ZIP containing PDF, CSV and exact request JSON. UUIDs identify records even when IDs repeat. Enter observed N/E/Z in the downloaded CSV and upload it against the open request. Returned observations, signed deltas, and notes are retained separately from the canonical coordinates. A return requires at least one finite observed coordinate per record.

**Point reservations.** Assign an inclusive numeric range and crew. Active overlap and already used canonical numeric IDs are rejected. A revision using an active reserved ID is flagged. Releasing a reservation preserves its history. Assignment policy and review of whether a crew may use its own range remain the survey team's responsibility.

**Evidence and reports.** Select a current finding and attach a JPG, PNG, or PDF under 10 MB. The copied file is SHA-256 linked to its finding and snapshot. Select the evidence to include in the review ZIP; the package has a PDF, change CSV, exact JSON and selected original attachments. Export fails when a selected attachment is missing or its hash has changed. The report is saved in the project Reports folder and can be included by existing deliverable profiles.

**Readiness.** Required checks cover project CRS/units and QA context, reviewed findings, returned rechecks, reservation conflicts, a report for the current snapshot, and a reviewer acknowledgment for that same snapshot. Each check may be optional. Enabling **Enforce these checks for deliverable packages** makes the existing package action refuse delivery when a required check fails; by default the gate is off for existing projects. A changed project snapshot invalidates the acknowledgment and prior report for readiness purposes. Rechecks and reservations remain visible in history.

This is a survey screening and handoff workflow, not an automatic coordinate adjustment or professional certification. The visual overlay is local project coordinates without a basemap.
